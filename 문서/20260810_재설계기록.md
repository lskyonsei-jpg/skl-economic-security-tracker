# JLOP BERT 업데이트 재설계 기록 (2026-08-10)

## 왜 다시 짰나

기존 구조는 **JLOP가 만든 엑셀(~2022) + 내가 받은 API 자료(2023~)** 를 이어붙인 것이었다. 여기서 세 가지 문제가 확인됐다.

### 1. 2022/2023 경계에서 값이 갈라져 있었다

같은 열인데 위아래 정의가 달랐다. JLOP 쪽 칸에는 JLOP가 정제한 값이, 2023년 이후에는 GTA 원값이 그대로 들어갔다.

| 중복 쌍 | ~2022 일치율 | 2023~ 일치율 |
|---|---:|---:|
| `MAST_chapterName` ↔ `gta_full_Mast Chapter` | 0.18 | 1.00 |
| `ImplementationLevel` ↔ `ImplementationLevel_clean` | 0.75 | 1.00 |
| `MeasureType` ↔ `gta_full_Intervention Type` | 0.87 | 1.00 |

가장 심각한 건 MAST 분류다. 16개 값 중 9개만 겹쳤다.

```
~2022  "Subsidies (excluding export subsidies)"   20,312건
2023~  "Subsidies (excl. export subsidies)"       10,494건
~2022  "Export-related measures"
2023~  "Export-related measures (incl. subsidies)"
~2022  "Intellectual property"  →  2023~  "Intellectual Property"
```

전 기간을 `groupby`하면 최대 카테고리인 보조금이 두 줄로 쪼개진다. 양쪽 숫자가 모두 그럴듯해서 눈으로는 잡히지 않는다. `ImplementationLevel`은 `NFI`/`IFI`(~2022) vs `nfi`/`ifi`(2023~)로 갈렸다.

### 2. 39열 중 실제 정보는 20개뿐이었다

- JLOP식 파생 칸 18개 + BERT 3개 + `gta_full_` 18개 = 39
- 앞의 18개는 뒤의 `gta_full_`에서 다시 계산 가능한 파생물
- 그런데 `gta_full_` 18개도 GTA API 29개 중 17개만 담고 있었다

즉 **불완전한 원본 + 그 원본의 중복 가공품**이었다. `gta_full_Affected Products` 한 열이 파일 문자열의 27%(29MB)를 차지했다.

### 3. 발표일 기준 수집이라 지연 등재를 놓쳤다

`announcement_period`만 썼다. GTA는 발표일이 아니라 등재일에 자료를 올린다.

```
7월 3일   조치 발표
8월 10일  업데이트 실행 → 아직 GTA에 없음
8월 15일  GTA가 뒤늦게 등재
8월 17일  "8월 11일 이후 발표분" 조회 → 발표일이 7월이라 안 걸림 → 영구 누락
```

## 새 구조

- 자료 원천을 **GTA API 단독**으로 바꿨다. JLOP 엑셀 의존을 제거하고 2010–2022도 직접 BERT로 분류한다.
- 열은 **GTA API 29개 + BERT 라벨 3개 + BERT 신뢰도 2개**. 중복 가공 칸을 전부 없앴다.
- 파일은 `intervention_description` 유무로 33열 / 34열 두 개.
- **매 실행마다 전량을 다시 받고 직전 스냅숏과 전수 대조한다.** 수집이 15분이라 감당 가능하고, 이렇게 해야 지연 등재·삭제까지 잡힌다. 사용자가 검증 구간을 지정할 필요가 없어졌다.
- 변화를 **신규 / 지연 등재 / 수정 / 삭제** 넷으로 나눠 보고하고, 수정분은 BERT 라벨이 바뀐 것과 안 바뀐 것을 구분한다. 승인해야 엑셀을 만든다.

### 검토했지만 안 쓴 것

- `submission_period`(등재일 필터), `update_period`(수정일 필터)로 증분만 받는 방식을 검토했다. 전량 수집이 15분이면 충분히 싸고, 전량 대조를 해야 **삭제된 건**까지 잡히므로 전량 방식을 택했다.
- `affected_products`의 `prior_level`/`new_level`(관세율 전후, 품목행의 46.9%에 존재)은 열 하나로 누르면 지저분해져 넣지 않았다. 필요하면 별도 파일로 뽑는다.
- JLOP 원본 라벨 보존 열은 넣지 않았다. 원본 엑셀이 `../원자료/260718_BERT_Expansion/`에 그대로 있어 필요할 때 대조하면 된다.

## 1차 자료 확인 결과

`원자료/Rawdata/GTA_API/`의 공식 문서로 확인했다.

- **API가 주는 열은 29개.** `2026 GTA - OpenAPI schema.json` → `components.schemas.InterventionFullListPublicSerializerV2`가 properties 29개, required 25개. `intervention_description`은 4번째 필드로 이 안에 포함된다. required에서 빠진 4개는 날짜 필드(`date_announced`, `date_published`, `date_implemented`, `date_removed`)이며 접근 등급과 무관하다.
- **Full Access는 열 개수를 늘리지 않는다.** `2026 GTA - GTA API endpoints.md:75` 기준, 등급 3 키가 제한 키보다 더 받는 건 `affected_products`의 관세율, `intervention_description` 전문, `state_act_source`, `is_official_source` 넷의 **내용**이다. 행 수는 등급과 무관하다.
- **응답은 wrapper 없는 bare array이고 `count` 필드가 없다.** `2026 GTA - API Quickstart.md:40`. 총 건수를 미리 알 수 없어 진행률은 누적 건수로만 표시한다.
- **스키마와 실제 응답이 다르다.** 스키마는 `implementing_jurisdictions`, `affected_products`, `affected_sectors` 등을 `string`으로 적어놨지만 실제로는 객체 배열이다. 코드는 실제 응답 기준으로 짰다.

23,277건(2023-01-01~2026-08-10) 실측으로 확인한 Full Access 4개 필드:

| 필드 | 실측 |
|---|---|
| `affected_products` 관세율 | 품목행 2,038,982개 중 955,945개(46.9%)에 prior/new |
| `intervention_description` | 22,784/23,277(97.9%), 중앙값 1,127자, 최대 14,459자 |
| `state_act_source` | 23,275/23,277(100.0%) |
| `is_official_source` | True 16,158(69.4%) / False 7,119(30.6%) |

## 성능 실측

`cache/`, `logs/` 타임스탬프 기준 (2026-08-10 실행).

```
API 23,277건 수집     5분
BERT 736건 분류       5분 18초  = 2.3건/초
엑셀 2개 저장         8분
```

GPU 없음(`torch 2.7.1+cpu`, Intel Iris Xe 내장, NVIDIA 없음). 최초 전량 분류는 약 68,000건이라 **8시간 안팎**이 걸린다. 이후 실행은 캐시 재사용으로 몇 분이면 끝난다.

양자화·ONNX로 CPU 추론을 빠르게 하는 길이 있지만 라벨이 미세하게 달라져 재현성을 해치므로 쓰지 않았다.

## 개발 중 잡은 결함

오프라인 테스트(캐시된 API 응답 23,277건 + BERT 스텁)로 잡았다.

1. **`compare()`가 KeyError로 죽음** — `set_index("intervention_id")` 뒤에도 비교 대상 열 목록에 `intervention_id`가 남아 있었다.
2. **parquet 왕복만으로 22,574건이 '수정'으로 잡힘** — `join_nested`가 `pd.NA`를 반환하는데 parquet를 거치면 object 열의 결측이 `None`이 된다. `str(pd.NA)`는 `"<NA>"`, `str(None)`은 `"None"`이라 멀쩡한 행이 전부 수정으로 잡혔다. 매 실행 리포트를 통째로 무의미하게 만들 결함이었다. 비교 직전에 결측 표현을 하나로 통일하는 `as_text()`로 해결.
3. **PowerShell 스크립트가 파싱 실패** — Windows PowerShell 5.1은 BOM 없는 `.ps1`을 ANSI로 읽는다. 한글을 넣으면서 깨졌다. UTF-8 BOM을 붙여 해결.
4. **`.cmd`의 인코딩 충돌** — `chcp 65001`과 CP949 한글이 충돌했다. `.cmd`는 ASCII 전용으로 두고 한글 출력은 PowerShell·Python이 담당하게 했다.

## 이전 구조에서 함께 고친 것

1. `load_prediction_cache()`에서 라벨 일부만 결측인 행이 오면 `int(nan)`으로 죽던 문제
2. 저장 후 재검증이 두 출력 파일끼리만 비교해 함께 망가지면 통과하던 문제 → 메모리상 결과와 대조
3. 네트워크 예외가 재시도 없이 전파되던 문제 → `requests.RequestException` 재시도 경로에 포함
4. 최초 설치가 중간에 실패하면 `.venv`만 남아 이후 영구 고장 → 설치 완료 마커 도입
5. `$env:GTA_API_KEY = $null`이 변수를 지우지 않던 문제 → `Remove-Item Env:`

## 남은 판단거리

- 관세율 전후(`prior_level`/`new_level`)를 쓸 일이 생기면 품목 단위 별도 파일로 뽑는다. intervention 단위 표에는 안 맞는다.
- `state_act_source`와 `is_official_source`가 이제 열로 들어온다. 비공식 출처가 30.6%라 "공식 출처만"으로 다시 돌리는 견고성 검사를 붙일 수 있다.
- `ticker` 엔드포인트(`POST /api/v1/gta/ticker/`)는 쓰지 않았다. 전량 대조로 같은 정보를 얻고 삭제까지 잡히기 때문이다. 수집 시간이 문제가 되면 그때 검토한다.
